## 1. 美术方向

**体素，但不是 Minecraft。** 参考：《Minecraft》的方块语言 + 《Trove》的高饱和调色 + 吉卜力的"植物是有意图的"。

三条硬规则：

1. **一切植物都有"想做的事"**：果实自发光（想被看见）、藤蔓向下（想找水）、蘑菇成环（想圈地）。
2. **建筑是长出来的，不是砌的**：灯笼镇的房子是木框架 + 苔土填墙；星坠堡是城砖 + 辉石灯；果园遗迹是一圈断墙围着谷地最老的树。
3. **光只有三种来源**：太阳/月、辉石与余烬（自发光方块）、果实（果实方块自己发光，摘下来拿在手里也发光），以及一种动物（灯水母的部件是自发光做的——但**谷地没有任何一具你能穿的身体会发光**）。**没有环境补光**——夜里没带荧光菇就是真的看不见。

### 面光照（烘焙，非实时）

每个面按法线给固定亮度，再叠顶点 AO：

| 面 | 亮度 |
|---|---|
| +Y（顶） | 1.00 |
| +Z | 0.88 |
| +X | 0.78 |
| −X | 0.66 |
| −Z | 0.58 |
| −Y（底） | 0.42 |

AO 四档：`[1.00, 0.78, 0.60, 0.46]`，按顶点三个邻块（边、边、角）计算。

这张表是给有硬边的方块用的。方块可以声明 `soft: 1`：面之间的明暗次序还在，但最低不低于 **0.74**，而且完全不吃 AO（`SOFT_S = 0.55 + 0.45·s`）。需要它的是云（16）：云也是方块，所以它以前也走这张表、也吃周围云层给的顶点 AO，一块被上面的云压着的底面测出来是自身颜色的 0.42 × 0.46 = 0.19。云本身是 94% 的白，于是结果是一团飘在亮天空里的深灰疙瘩——看起来就是天上的一块黑。画面里量：一朵云现在平均 **113**，它背后的天空是 92；把这个标记去掉，云平均 **70**，比它背后的天空还暗。灰障的墙是用同一个方块做的，所以灰障现在看着像淡雾柱子，而不是像石头。

树冠用同一个标记，理由也一样。一团树冠就是一堆叶子方块，它的底面就是你站在树下时看到的那个面，而 AO 在它下面采到的那一圈邻块**就是**这团树冠本身：树下那圈暗就是树。所以五个树冠方块（树叶 7、针叶 8、银叶 9、暗叶 27、柳叶 28）也都是 `soft: 1`。

这之后剩下的就是 AO 本身：它问的是"这块面在不在缝里"，却被当成明暗规则来读。一块朝着开阔天空的面按定义不在缝里，可树冠的底面却拿到最暗那一档，因为围着它的那圈实体正是同一团树冠。所以现在每块面还要问一遍：沿自己的法线看出去，多远才碰到东西——连续 `OPEN_R = 4` 格干净空气就完全不吃缝隙压暗；两格之内就有实体就全额保留，那正是山崖、屋檐和洞口需要的那道接触阴影；两者之间按比例插值。底面也会往 soft 的底面亮度抬上去，因为表里把底面压到 0.42 的理由是"没人会去看底面"，而这一条对一块悬在开阔空气里的面并不成立。

全图量一遍，只数那些沿法线有连续八格干净空气的面——也就是玩家会衬着天空看到的那些面，共 107,880 个：改之前 **60,506** 个渲染出来低于 60/255，占 56%，平均 73，最差 10。只加曝光这一项降到 19,277（18%）；再加上树冠的标记，**15,421 个（14%）**，平均 93，最差 39。剩下的是面表在照吩咐办事：一块暗方块的 −Z 面就是暗，那是那个假太阳，不是洞。把这条射线放宽成五条里取最宽的一条也量过，没有任何变化，所以射线保持笔直。多出来的这条射线量不出代价：100 个 chunk 整图重建前后都是 ~100 ms。画面里量同一件事：全图 216 个视角，亮度低于 55、且五像素内有亮度高于 130 的天空的像素，从占画面 **1.46%** 降到 **0.68%**。同一个指标在两个低太阳的时刻（07:00、17:00）是 **0.53%**，所以正午是最坏的情况，不是最走运的一次。`game/test/play.js` 在玩家真的会站到的两处读画面——一棵针叶树冠底下，和灯笼路上方那圈城镇屋顶：悬着的面可以比天空暗，但它的像素至少四分之一要到 **45**/255、最暗的二十分之一要过 **35**。把着色改回去，树冠这两个数是 31 和 24，屋顶是 22 和 19。

### 生物模型

体素部件拼装，每部件一个网格 + 一个 pivot。部件可以声明 `parent`，于是四肢有了关节——肩到肘，髋到膝。部件按绑定姿势书写，而猫头鹰的绑定姿势是收拢的翅膀：栖着的猫头鹰才是你一天里看得最多的那个形状。

**所有模型都朝 +Z**，而这个游戏里"朝向 `yaw`"指的是方向 `(sin yaw, -cos yaw)`：yaw 0 是北（-Z），yaw 往 +X 增大。把 +Z 转到这个朝向的旋转因此是 `PI - yaw`，而且它只存在于一处：`M4.faceY`。写成 `yaw + PI`（三个调用点以前都是这么写的）只有在正南正北时才碰巧正确，其余朝向都会把身体沿 Z 轴镜像：从背后看，往东走的身体露出的是脸；第一人称的手指向侧面；谷地里的动物只要往东或往西走就是在倒着走。`camera` 那一步的角度检查看不见这件事——镜像的模型角度一模一样——所以 `game/test/play.js` 改读画面：把身体摆在四个正方向上各站一次，镜头在它背后，把头顶投影到屏幕上，要求每一个方向看到的都是后脑勺（头发），而不是脸。

| 动画 | 用途 | 公式 |
|---|---|---|
| `flap` | 上臂（翅根） | `rz = −sign·beat·(0.22+0.78·air)`，`beat = sin(t·11)·flap`，下拍满幅、回收只有它的 0.42。对称的正弦是风车；下拍硬、回收软才是翅膀。`flap` 是这身体正在**用多大力**拍翅——见下文"拍翅属于往上爬" |
| `fold` | 前臂（parent 是翅） | 只在上拍折叠：`rz = sign·(beat<0 ? −beat·0.5 : 0)·air` |
| `walk` | 大腿 / 上臂 | `rx = −asin(sin(0.9·stride·amp)·footAt(u))` —— 把脚放到它这一步里该在的位置上的那个角度。`u = gait + (sign < 0 ? 0.5 : 0)` 是这具身体在自己这一步里的位置：一步地面就是一个整周期，身体两侧相差半步，而这个数是按身体**实际走过的地面**推进的，从来不是按时钟。`stride` 是这个部件自己占这份摆动里的多少：雨蛙的腿一点不占，因为雨蛙在陆地上不是走路，是跳 |
| `knee` | 小腿 | 膝盖只朝一个方向弯，而且只在脚离开地面的那一段弯：`rx = bend·0.62·stride·fold(u)·move`，`fold(u)` 在支撑段一点没有、只在摆动段起一个包。什么时候弯由这一步自己说，不由时钟的四分之一程说：一个没有脚踝的模型，一只弯着的、还踩在地上的膝盖没有别处可去，只能往下。`bend` 说的是这个模型的膝盖朝哪边弯（不写就是人的那种朝法），而 `sign` 的镜像**故意不加**在弯折上 |
| `elbow` | 前臂 | 同样的弯折长在手臂上，幅度小些，而且总留一点挂着，**并且身体越是快，这条手臂就被端得越是弯**：`rx = bend·(0.12+0.3·fold(u)·move+0.55·move²)` —— 一条笔直垂着的手臂就是一根棍子，而一条笔直的手臂每秒被甩过 2.3 个步子，就是一具身体每步都要把它刹停再重新启动两次的钟摆。站着的身体仍然保持 **0.12 弧度**，走路的身体仍然让手臂垂着（**0.14**），跑起来的身体是把它端着的（整个支撑段保持 **0.61**，摆动最宽的那一刻到 **0.89**）。手臂与同一侧的腿反向摆，这是那半步 `sign` 买到的 |
| `twist` | 躯干 | `ry = footAt(u)·move·0.16` —— 腿以上的那一截与腿反向转，走在步子上而不是时钟上；否则只要速度不是时钟恰好同意的那一个，肩和脚就是两件互不相干的事 |
| `nod` | 头 | `rx = sin(t·1.9)·(move·0.06+0.02)` |
| `wag` | 尾 | `ry = sin(t·1.6)·(move·0.5+0.12)` |
| `bob` | 身体 | 在天上时它**就是**拍翅的节奏：`dy = −max(0,beat)·0.16`，翅膀往下压，身体就往下沉。两条互不相干的正弦，会让飞行的身体看起来像一具身体上螺栓固定着两个会动的零件。起伏跟着**这一拍**走、不跟着时钟走，所以收着翅膀下滑的身体只沉 0.024 m，而不是 0.16 m。在地上，起伏就是这一步：`dy = rideOf(stance)·cos((u−stance/2)·4π)·move·0.20 + sin(t·2.2)·0.05` —— 一步两次，因为身体此刻站在这条腿上、下一刻站在那条腿上。**而它是正着来还是反着来，取决于这一步里有没有一段是腾空的。** 只要总有一只脚在地上，腿就是**撑杆**：身体在支撑段的正中最高，因为那根撑杆正好笔直在它下面。一旦支撑段短过一步的一半，每一步里就出现一段没有任何脚着地的时刻，腿就不再是撑杆而是**弹簧**——它落到一只脚上、把它压弯、再被弹回来——于是身体在支撑段的正中**最低**，在腾空段的正中最高。`rideOf(stance)` 就是这个翻面：支撑段达到一步的一半或更多时是 1，到 `STANCE_RUN`（0.30）时是 −1，中间渐变。一个人以 4.7 m/s 跑时支撑段是 0.319，所以旧的起伏（永远在支撑段正中最高）恰好把身体抬到最高点，而那一刻它的腿正在承受全身的重量。从画面要上传的角度上量、量满整整一步：一个人以 4.7 m/s 跑，一步之内起落 **0.055 m**，最低在 **0.158** 处（支撑段正中是 0.16），最高在 **0.408** 处（腾空段正中是 0.41）；走路时支撑段是 0.556、没有腾空段，于是正好反过来——最高在 **0.279**（支撑段正中 0.278），最低在 **0.029**（两只脚交替换班在 0.028）。棕熊 **0.073 m**，猫头鹰 **0.046 m**，都按自己的速度；而且这个起伏越是快越值钱：最高速的 0.35 处是 0.025 m，0.94 处是 0.055 m。以前它是一条自己的正弦：一只熊按自己的速度每秒走 2.8 步，身体却每秒上下一共 0.35 次。闲着的部分仍按时钟走；没有会走路的腿的身体也没有步子可骑，它整条都按时钟走。人自己的身体以前根本没有起伏，现在它挂在胯上、有了；而它站着的那些腿把这份起伏抵消掉，所以身体在上面骑着步子、脚却还钉在地上 |
| `pulse` | 雨蛙的喉、水母的伞 | 是缩放，不是旋转 |

**踩到地面的脚，就停在那儿。** 走路这套循环以前是所有有腿的身体共用一个时钟——髋部 `sin(t·7)`，步频是个常数——而身体是被自己的速度推着走的，这两件事从来没打过招呼。按渲染上传的矩阵读出来：一只熊的脚沿着地面以 **2.3 m/s** 移动，而它的身体以 **2.1** 前进；一个人是 **3.0** 对 **4.1**。一只脚五帧里有四帧踩在地上，却没有一帧是停着的——整只动物是在草地上溜冰。这不是调参能解决的。脚正好在正弦弧线的最低点，而那也是一条正弦转得最快的地方：摆动最快的那一刻，恰恰是脚必须最慢的那一刻，什么速率都修不好。于是循环按它本来就有的两个动作写，由地面来打拍子。`footAt(u)` 说脚在自己这一步里走到了哪：支撑段是一条从 +1 到 −1 的直线，因为踩在地上的脚是被身体带着沿一个平面走的，只有直线能把它留在那儿；摆动段是一条两端都缓下来的曲线，从 −1 回到 +1，而这一步里只有这一段允许膝盖弯。支撑段占整个周期的份额也不是常数——走路时 **62%**，身体最快时 **30%**——快的那一步剩下的路程是身体带着脚在空气里走完的，这就是不用把任何腿摆得更开也能得到大步子的地方。髋角就是能把脚放到那个位置的角度，而且它是负的：绕 x 的正向转动会把垂在铰链下的脚带向 −z，而这里每个模型都朝 +z。摆多大（`amp = move·stance/0.62`）是决定速度怎么变成步子的那个旋钮，而两种显然的拧法都不对：摆得更大，快的身体就走又长又慢的步子；保持摆幅、把支撑段缩短，就走又长又快的步子——两种情况下步频都随身体变快而**下降**，而身体做的恰恰相反。身体做的是几乎保持步频不变、改变步幅：一个人 1 m/s 走路时步子约 0.4 m、每秒约 2.5 步，4.7 m/s 跑起来步子 1.9 m、每秒还是约 2.5 步。让摆幅正比于速度**乘以支撑段**，正好让两者在它们必须抵消的那一处抵消掉：步长正比于速度，而步频成了腿自己的属性。一个周期在地面上值多少同样不是常数：它每个模型量一次，量的是这个模型自己的脚掌在身体下方沿前后真正够到的距离，用的就是上传给渲染的那套矩阵——位置最低的铰链并不是脚挂着的那个，而让脚不陷进地面的抬升会移动整条肢体——然后调用方按身体走过的地面推进相位，于是一个周期正好把身体带那么远。在一段平地上按每个身体自己的速度走一遍量出来：人 4.7 m/s 时步长 **1.85 m**，模型自己给的数是 **1.85**；熊 5.2 m/s 时 **1.95 m** 对 **1.96**；猫头鹰 **0.41 m** 对 **0.40**。人每秒 **2.33** 步，熊 **2.29** 步；2 m/s 时步频不变，步子不到一米。脚也确实钉住了：在模型说脚踩在地上的那些帧里，脚走过的地面是身体在同一批帧里走过的 **0.006**（人）和 **0.014**（熊）——剩下的是没有脚踝的脚在腿扫过身体下方时从脚尖到脚跟的滚动——而以前这个数大于 **1**。站着的身体根本没有步子：腿停下，两秒里脚移动 **0 m**；一具顶着墙走的身体用它的身体停下它的腿，而不是原地踏步。有一个数还没对，写在这里而不是藏起来：猫头鹰以 **6 m/s** 穿着 **0.4 m** 的步幅，也就是每秒 **14.9** 步、在这个帧率下一个周期只有四帧。步长正是这具身体的腿应得的那个值；不匹配的是速度和腿，那是关于这具身体的记录的问题（04 §4），不是关于循环的问题。
部件还可以声明 `air:[rx,ry,rz]` 和 `crouch:[rx,ry,rz]`：身体离地时它取什么姿势、腿在蓄力时它取什么姿势。权重来自物理，不是来自"现在画的是哪种动物"的猜测——`air` 是身体实际离地多高，`crouch` 是它的脚从上次起跳后在地上停了多久，`squash` 是它落地时的速度，作为缩放作用在整个身体上。不跳的身体永远不会被画成在跳。身体踩着的那条腿用 `stands: 1` 说明这件事，于是它离地时的姿势只跟到身体实际离地那么远——`off` 就是调用方按身体高度量出来的那 0..1 的离地量。这不是为了整洁：一条比身体还高的后腿，在进这个姿势、和出这个姿势的路上，会把脚整个扫过它正踩着的那个平面，因为姿势是缓动的，而身体自己的原点并不跟着它走。从画面上读：一只雨蛙落回它刚踩过的那片地时，把小腿插进地里 **0.154 m**，在 **360** 帧里占了 **169** 帧——而那会儿那个姿势离地面还远得很。

部件还可以声明 `swimKick: 1`（身体在游的时候，这一部件是蹬腿的驱动件）、`heldPose: [rx,ry,rz]`（水把身体托起来时它被保持在这个姿势）和 `swimPose: [rx,ry,rz]`（游的时候它被保持在这个姿势）。`swim` 和 `held` 是调用方传过来的第四个和第五个信号。`swim` 是一个**比例**、不是一个开关——身体此刻实际游得多接近它自己记录里写的那个游速；数据没给它游速的身体则是 0：**人在湖里是趟水**，因为人的模型没有游泳部件，游戏里也没有人的泳姿。它过去有个 0.18 的下限，好让一个正在滑停的身体也继续蹬水、而不是慢慢收住，而「青蛙悬停不动时脚还在动」这个抱怨正是从那个下限来的：一具被水托着、哪儿也不去的身体，在四秒一动不动里把两只脚走了 **1.55 米**。如今这个比例由调用方递进来（游戏循环里的 `strokeOf`），按身体此刻实际在推的水定大小，所以一个哪儿也不去的身体根本没有泳姿：它的腿就停在水托着它的那个姿势上。`held` 是水把身体托住——在水里、用鳃呼吸、脚没有踩到底——和物理判断一具身体浮不浮用的是同一个读法（03 §4）；正是它把膝盖折起来、把脚放到身体**后面**而不是身子底下，也顺手把整条腿往外**转离中线**。只折膝盖，腿还是钉在体侧上的：同样从那些矩阵上读，一条小腿探出体侧 **0.063 米**，而身体半宽只有 **0.169 米**，它的脚心离中线 **0.152 米**——从正后方看，一只雨蛙就是一条扔在水面上的裤子。往里卷，腿反而走向了另一头：漂着的时候一只脚探过自己身体的中线 **0.115 米**，游的时候 **0.119 米**，两只脚都朝内，腿只探出体侧 **0.024 米** 和 **0.052 米**——从正后方看，一只雨蛙就是两条在自己身子底下交叉的腿。在胯上往外转 0.1 弧度、在膝上再转 0.1 弧度之后，脚心落在自己那一侧：漂着是 **0.234 米**，游起来是 **0.272 米**，两只脚再也碰不到中线（整套泳姿里最接近的一次也只有 0.001 米），腿探出体侧 **0.147 米** 和 **0.176 米**；这一转分给两个关节、而不是全挂在膝盖上，因为过去只给膝盖的那 **0.5 弧度** 会把整条腿甩到体侧外 **0.218 米**，一只贴着湖壁漂着的雨蛙就把脚插进了石头里。陆地上腿还是探在体侧，雨蛙的大腿本来就是这样：**0.078 米** 和 **0.181 米**，而水里这个姿势正是照着它来比的——水里的腿探出去是陆地上那条大腿的两倍多，而蹼足正是为了划水才要探出去；探得最宽的一次出现在慢速的泳姿上，一只按自己巡航速穿过湖的雨蛙把腿带到体侧外 **0.192 米**。站在水里的身体——踩在湖底上，或者在水只有一格深的地方趟水——有脚可站，也就不蹬了：在那儿蹬腿是一具身体在对着空处蹬。被水托着、哪儿也不去的身体腿也不动：它的脚移动 **0 米**，水托着它的那个姿势就是全部。雨蛙不在水面上跑，也不踩着一条正弦划水。两条后腿**一起**划，一个泳姿 **1.5 秒**（泳姿自己的时钟是 `SWIM_RATE` = 4.2 弧度/秒），而不是步频的每秒 7 步；这个泳姿是雨蛙的蛙泳，写成四个关键帧，关节在它们之间缓动——**滑行**：两条腿在身后并拢、甩得笔直（膝盖 **140 度**，两脚相距 **0.47 米**）；**收腿**：两膝分开、小腿折起来贴住大腿，于是每只蹼足收到自己那条胯旁边，在身体后部底下、从不在身体中段底下（膝盖低到 **52 度**，两脚张开 **0.54 米**）；**蹬腿**：膝盖伸开，两只脚一起向后、向内射出去（相距 **0.17 米**，膝盖蹬到 **175 弧度。量的是画面：从正后方看的轮廓，与它自己的镜像吻合度，一次划水的两个极端分别是 **0.965** 和 **0.957**；而这两个极端彼此之间只吻合 **0.559**——腿确实在两者之间来回动。画面这一头是这对检查里松的那一半——从正后方看，一条腿在前、一条在后只让轮廓变 6%——所以这个说法同时也在角度本身上读一遍，那才是它真正被说出来的地方。脚本身也顺着渲染器要上传的那两个关节矩阵跟到底，量在游得最快的那一帧上：脚心从身体后缘**往后 0.26 米**扫到**往前 0.07 米**——离身体中段还差 **0.10 米**，从没到中段底下——一共扫 **0.33 米**，上下起 **0.19 米**：收起来的那只脚最高，升到模型原点之上 **0.22 米**，那正是它自己那条胯挂着它的高度（**0.23 米**），也远在身体背脊（**0.33 米**）之下；蹬出去的那只脚最低，在 **0.04 米**。膝盖折到 **52 度**、再甩回去到 **175 度**，从不蹬过直。一只按自己巡航速穿过湖的雨蛙扫 **0.18 米**，最远处脚在那条后缘后面 **0.17 米**；一只漂着哪儿也不去的身体扫 **0 米**，两只脚就留在后缘上；而站在水里的身体保持着它在干地上那个姿势，脚在后缘**往前 0.18 米**，两个姿势相差不到 0.002 米。 转弯也是蹬出来的，不只是侧倾：调用方交进来的 `turn` 是**带符号**的航向角速度（rad/s），划水的侧向幅度按它缩放，于是转弯外侧的那条腿咬得更深（系数 `TURN_KICK` = 0.7，在 `TURN_FULL` = 1.9 rad/s **1.02 米**，内侧只有 **0.29 米** 和 **0.72 米**——外腿划出的距离是内腿的 1.41 倍——外侧腿也比内侧腿站得再开 **0.04 米**；它的膝盖仍然折到 **35 度**，脚仍然待在身体后方、从不跑到中段底下（抬起 **0.25 米** 对划出 **0.37 米**）。直着走的身体 `turn` 正好是 0，两条腿划得一模一样；向左转与向右转给出同样的数字，只是两条腿互换。

**身体本身有两个姿势信号：`bank`（转弯时侧倾）和 `tilt`（鼻尖朝着正在走的路）。** 被空气或水托着的身体转弯时向内侧倾，并且指向它实际正在走的那条路线；用脚走的身体两样都不做，因为脚咬得住地面，地面会回应。两个都不是部件动画——渲染器把整个身体先绕它自己的朝向轴转，再绕它自己的横轴转——而且玩家的身体和每一只生物用的是同一条规则、同一组数。侧倾是"这条弧线需要的横向推力"除以"翅膀要对抗的那个拉力"：`atan(每秒转过的弧度 × 速度 / 9.8)`，夹在 0.45 rad 以内，再以 4.5 缓动。游戏自己的重力是 23 m/s²，因为跳跃的手感需要它；这里**故意不用**那个数，因为侧倾不是下坠。俯仰是同一个想法横过来：`atan(−爬升率 / 速度)`，夹在 0.6 以内，以 4.5 缓动，机头朝下为正；爬升率就是这具身体刚升高或降低的那一段高度。量出来：一具被按着沿固定路线游的身体峰值 **0.427 rad**（24°），一具飞的身体峰值 **0.445**（25°）；同样两具身体被按着走直线，峰值是 **0**；一头棕熊被同样转过四分之一圈，始终是 **0**；一具放开高度往下落的稳定在机头朝下 **0.542**，一具往上爬的在 **−0.31**，一具用脚走的在 **0**；把俯仰从绘制里拿掉，这些帧改变的 **517** 个像素里只剩 **0** 个。两处豁免，豁免的都是身体：睡在枝上的鸟原地转身，那不是侧倾；一把会搏动的钟没有鼻尖可指，所以灯水母只侧倾、不俯仰。 交给侧倾的转弯速率是**带符号**的，而它以前不是：侧倾过去是用航向变化量的绝对值算的，所以任何身体无论往哪边转都朝同一边侧倾——向左转是往弯里倾，向右转就是往弯外倾，而两条腿的蹬也就没有可信的依据可比。这个速率还带一个 **0.12 rad/s** 的死区：一个在水里爬、还蹭着岸的身体每帧读两次的航向会抖上一两度，建立在抖动上的侧倾会让一具笔直游着的身体左右晃肩。量过：直着走的身体现在在整个 **94** 帧里 `turn` 都正好是 0；被赶着转过四分之一的身体峰值 **1.46 rad/s**，两条腿的蹬互相镜像到 **0.02** 以内。

**有身体的东西都不在原地转身。** 被空气或水托着的身体弯的是它已经在走的那条路线，每秒最多弯 `turn` 弧度——动物记录上有这个字段，同一个物种的形态记录上是同一个数，因为那只动物和用它做出来的身体是同一具身体：猫头鹰 1.4，雨蛙 1.9，棕熊 1.6，灯水母 0.8，人 1.6。超过它自己的巡航速度之后，弧线只会更宽、转弯不会更快，因为同样的推力要甩动的是更多的身体；这个速率还被另外夹了一道，上限是"它偏离航线多少"的 2.2 倍——这一条正是让一具身体不再左右乱摆的东西，因为它指着的地方和它正在走的方向会不一致。量过的旧数据：一具蛙梨形态在水里开一个转弯，起始角速度是 **94 rad/s**，横过镜湖的速度是 **9.9 m/s**，而它自己记录里写的游速是 4.6 m/s；一具 owlberry 以 **4.2 m/s** 在飞，而记录里写的是 7.0，转过 90° 只用 **1.03 s**。之后：峰值 **1.90** 和 **1.40 rad/s**，绕一整圈的整个过程里速度都保持 **4.63** 和 **6.97 m/s**，与记录相差不到 0.04；四分之一圈要 **1.77 s**。路线确实是一条弧：雨蛙的路线沿弧量是 **3.16 m**、两端直量是 **2.98 m**，猫头鹰是沿 **13.43**、直量 **12.17**，而被按着走直线的身体沿 **3.16**、直量也是 **3.16**。用脚走的身体**故意**不做弧线限制：脚咬得住地面，用脚走的身体转弯是在回答鼠标，不是回答舵。

**做不到的那个转弯，动物会慢下来做。** 转弯的弧长等于速度除以速率，所以一个比这条弧还近的地方、或者一个偏在一旁的地方，就是动物会绕着转、永远到不了的地方。让那个圆正好经过那个地方的速度来自几何：到那个地方的连线是这个圆的一条弦，而一条与航向夹成航线误差的弦，属于一个半径等于"距离的一半除以那个误差的正弦"的圆。那个想当然的上限——距离除以正弦、不带那个一半——正好就是动物以自己的弧宽永远绕圈的速度：一只猫头鹰被送到身旁 1.8 m 的一个地方，25 秒里绕着它走了 **73 m**，从来没有进到 **1.79 m** 以内。同样三趟差事，之后量出来：猫头鹰站在离那地方 **0.8 m** 处，一共走了 **1.9 m**；一只雨蛙离一个 1.2 m 外的地方 **0.79 m**，一共走了 **1 m**（之前：绕它走 48 m）；一盏灯水母离一个 0.9 m 外的地方 **0.8 m**，一共走了 **0.4 m**（之前：绕它走 23 m）。在开阔处，地方远、正弦小，这条规则什么都不花；近了，它看起来就是动物在转过来之前收一步——它本来就是这个意思。

**遇到墙的动物会绕过去。** 它能迈的那四步里，它迈的是"地面站得住、而且最朝着它想去的方向"的那一步，航向跟着这一步走、按它自己每秒允许的弧度转——沿着障碍物的轮廓走，而不是重新领一趟差事。放弃就是旧行为的全部：北岭那两头棕熊在 **20%** 的帧里在走，九十秒里两个加起来走了 **24 m**，因为到了悬崖前面，这一步被拒、差事被丢下，然后同一块石头再撞上去（凑近了看同一对棕熊，眼前的那一步在 **2400** 帧里被拒了 **2024** 次）。之后：**94%** 的帧、**51 m**；而雨蛙——它们沿着整条湖岸遇到的也是同样的墙——从 **76%** 到了 **93%**。一帧只有一份转弯预算，谁花都一样：朝着差事转向和绕过障碍迈步各自都用了全额，于是一头抵在崖上的棕熊以 **3.2 rad/s** 转身，而它的身体只允许 **1.6**。

**拍翅属于往上爬。** `flap` 是调用方传的第五个信号，0 到 1：一具没有在向高度要东西的飞行动物把这一拍收到 **0.15**，靠翅膀滑着走，身体就在翅膀不再往下压的时候落下来（往下落时量到 **0.163**，一被要求爬升就是 **0.999**）。渲染器上传的摆幅和起伏跟着这个信号走，而不是跟着时钟走：满幅一拍把翅膀带过 **1.739 rad**、把身体抬 **0.16 m**；收着的那一拍把翅膀带过 **1.383 rad**、身体 **0.024 m**。动物身上是同一个信号——往下落的猫头鹰收拍，往上爬的猫头鹰满拍，睡在枝上的鸟把翅膀收在 **0**。

**脚踩在一个面上，就是站在这个面上。** 以前接触标记只由"碰撞不得不拦下来的那次移动"点亮；身体总是停在它上次撞到的那个面外 0.0005 m 处，而下面那一格要等脚探进去 0.001 m 才会被采到——所以一帧得先沉下 0.0015 m，脚下那个面才会重新被看见。陆地上重力够用（一帧 0.006 m），所以标记只是一帧一帧地闪，缓动的姿势把它盖住了。在水里它不够用：浮力抵掉大部分重量，阻力留下约 0.05 m/s 的终端下沉速度，一帧 0.0008 m，于是水底每三帧才被采到一次。于是在水深只有一格的地方趟水的身体——镜湖的湖岸有 183 个这样的列——它整个时间都站在湖底上，却被报成悬空：`air` 姿势缓到 0.42 就停在那里，转向只剩三分之一的推力（accel 12，本该是 34）。所以位移算完之后，脚在实体 2 cm 以内、身体又不在往上走，就是站着；2 cm 正是自动上台阶用来把身体放回它刚爬上的那道坎面的距离，也远小于身体真的离面之后攒下的落差（第一帧 0.006 m，第五帧 0.10 m）。量出来：站在这样一个列里，身体 **100%** 的帧都在底上、姿势是 **0**——改之前是 50% 和 0.42——沿着这条湖岸趟水，两秒走出 **5.19 m**，脚一直是落着的；而且这个标记不是胶水：身体走出一个单级台阶，接下来 40 帧里有 **18** 帧离地，姿势缓到 **0.88**，落下 **1.0 m**。

**没有脚踝的腿会抬起来，站着的腿拒绝被拖着下去。** 一条摆动的胯、或者一个弯折的膝盖，会把那只脚上朝着摆动方向的那个角，压到脚踩着的那条线之下。这件事发生时步态并没有错——只是模型少了一个关节，而这条腿只能靠抬起来补。于是在陆地步态里转动、并且它这条腿够得到地面线的每个部件，都带着它所转动的那些盒子的角——它自己的，以及挂在它下面的每个部件的（一条摆动的胯带着的是末端那只脚）——以铰链为原点量好；而它被抬高的量，正好是它自己这一转把这些角压到静止位置之下的那么多。抬起加在腿的**最上端**，所以整条腿一起动，胯和膝之间的那个关节不会张开。另一半是起伏：身体走路时骑的是自己这一步（`bob`，最快时是棕熊自己单位里的 ±0.25——0.20 是步子带来的，0.05 是闲着的呼吸），而腿挂在它下面，所以身体一沉就把脚一起带走——每一步、每秒两次、往地里 6 cm。踩在地上的那条腿不会跟着上面的身体抬起来时一起下去，所以它把那个起伏抵消掉，而且只有腿的最上端去抵消，否则这份抵消就被算了两遍。只有够得到地面线的腿才拿到这张表：前臂也摆、也落，但它那儿什么都不该动。对转动来说这份抬起是单向的——脚在摆动中可以抬起来，但不能沉下去——对起伏则是双向的。从画面上量，在同一片平地上走 180 帧、站 120 帧：棕熊的后脚在它步行的 **32** 帧里到了地面之下 **0.091 m**，猫头鹰的脚趾在 180 帧里的 **106** 帧是 **0.063 m**、120 帧里的 **17** 帧是 **0.055 m**，人的靴子 **32** 帧 **0.032 m**，雨蛙的小腿在 360 帧里的 **169** 帧是 **0.164 m**。改完之后：棕熊和人 **0.000 m**，雨蛙 **0.007 m**，猫头鹰一帧 **0.025 m**。哪一半关掉的是哪一个：膝盖的四分之一程滞后关掉棕熊和雨蛙，这份抬起关掉人的靴子（把它关掉是 **0.033 m**）和猫头鹰的步行（**0.064 m**），而下面那条俯仰规则关掉猫头鹰的站立（**0.071 m**）。而这份抬起不能把一条腿从它悬挂的部件上切下来，所以同一步还量了部件与它上面那个部件之间的缝：每个身体都是 **0**，上限 5 mm；为了证明这个检查有用而把猫头鹰的腿刻短，会在本该是胯的地方留下一条 **1.2 cm** 的天缝。一份起伏也被同样的界限卡着，那就是腿被埋进它悬挂其上的那个部件有多深：人的大腿盒只伸进胯盒 0.1 个自己的单位——1.8 cm——而一具在这个比例下骑 0.25 个单位步子的身体需要 4.5 cm 的重叠，于是把它们刻到 0.3 个单位。多出来的 2 cm 藏在胯盒里面，同一个颜色，看不见。

**一具为天空造的身体，脚一落地就是在地上。** 身体要的俯仰是它正在走的那条路的倾角，`atan(−爬升速率 / max(速度, 0.5))`，而身体越慢，这个问题读得越糟：翅膀那一支整帧都答"在天上"，不管碰撞器刚才说了什么，所以一只站在地上的鸟被塞了一帧重力（−0.38 m/s），而它的速度是 0，于是这被读成一次俯冲——`atan(0.38 / 0.5)` 就是 **0.65 弧度**。所以身体去问地面，而不是问那个标记：它比这一列里它该站着的高度高出多少，`y − standY(...) < 0.02` m，和台阶、和水的托力用的是同一个 2 cm——而且是在竖直那一支跑**之前**问，不是之后。而地面止住身体下落的那一帧，也止住身体的转动：落地把俯仰设成 **0**，就在设那下压扁的同一帧。从画面上量，一只静止站着的猫头鹰在它还站着的时候一直保持着 **0.60 弧度**的低头，脚趾到了它站的地面之下 **0.071 m**；走路时是 **0.055 m**。改完之后：站着俯仰 **0**，走路 **0**，脚趾站着 **0.030 m**、走路 **0.023 m**，而剩下的那几帧是一次下落的最后一刻——身体离水面还有几厘米，以 0.42 弧度往下落，脚趾在它落地之前有一帧穿过了水面。还在天上的身体照旧把鼻子对着它正走的那条路：往上爬 **−0.55**，往下落 **0.44**。

模型自己**不带缩放**。给身体定尺寸的只有一个数：`data/creatures.js` 里的碰撞盒（`size`，单位米）。模型用单位方块建模，生物的 `scale` 把单位换成米——所以模型和碰撞盒是同一具身体的两份写法，两者一旦不一致，玩家就会被自己看得见、却碰不到的几何体穿过去。`game/test/node-smoke.js` 会把每个模型按它所属生物的碰撞盒量一遍，超出就失败：模型的水平半径最多比盒子的半宽多出 0.1 m，最高点最多比盒子的高多出 0.06 m。量的是**半径**而不是宽度，因为碰撞盒是一个不随身体转动的正方形底面——正面刚好放得下的模型，转个身照样捅进墙里。这道闸门立起来之前，棕熊离中心有 1.26 m，而它的盒子只有 0.70 m 宽：等于有 0.56 m 的熊在它靠着的那面墙里，雨蛙的鼻尖也超出自己的盒子 0.13 m。

灯水母是唯一**没有盒子可量**的模型：游戏里没有任何东西会撞上它（你从灯中间游过去），而它不结果实，所以也没有玩家会穿上它。于是改用它图鉴上写着的尺寸来核对——按 `scale` 0.16 算，**宽 0.61 m，从伞顶到最长那条腕的尖端 0.74 m**。

5 个模型：human, owl, frog, bear, jelly。

### 3.2 渲染

- **分块**：16×48×16，10×10 = 100 块。每块 6 个网格：`[不透明, 自发光, 水, 道具, 道具自发光, 玻璃]`。
- **面剔除**：固体不透明邻居的面不生成。
- **视锥剔除**：从 MVP 提取 6 个平面（列主序取行：`row3 ± row0/1/2`），逐个 chunk 用一个**盒子**去测——就是 chunk 自己那个 16 x 48 x 16，而每个平面只回答它朝向该平面法线最远的那一个角，盒子要答的也只有这一个角。以前用的是一个半径 **15** 的球，球心在地图高度的一半处；而 chunk 自己的角离那个球心有 **26.5**，所以一个 chunk 要是屏幕上只剩它一个角，它会被整个扔掉，天上就破出一个洞。一个贴着镜湖水面的镜头往下 69 度，问世界「我前面站着什么」，在有答案的像素里有 **56,633** 个什么都没画：一片干天的灰楔子，正卡在湖底某个 chunk 的远角上，而那里正是湖底最深的地方。同样这片水，换两个镜头，同一个画面里这个洞是 **75,369** 和 **42,186** 个像素。测试是拿画面跟自己比——同一个镜头，一次按游戏真正跑的剔除画，一次完全不剔除画——现在湖上八个镜头两帧逐字节一致。这一点值得说，因为这八个镜头确实在扔整块的 chunk：全谷 100 块里每帧扔掉 **40** 到 **88** 块。
- **自发光层**：单独网格，`emisBoost` 提升，不受日夜光照影响。
- **水**：单独网格，而且它根本不带透明度。水面曾经是盖在画面上的一块有色玻璃：`BLOCKS[WATER].alpha` 写着 **0.72**，由 `def()` 一次性折进顶点颜色的第四个字节、绘制调用里不再抄第二份同一个数；0.62 的时候，湖底的明暗对比透过水面还剩下 38%，湖看起来像地上一个坑，而不是像水。它现在没了。水对光做的事是一条按颜色分开的定律：块表上 `fogK: [0.55, 0.16, 0.06]` 说的是这东西每一米吃掉多少日光、按颜色分开；同一条定律回答光穿过一片湖要走的每一段路。日光下来的那一段，烘进湖底的顶点里，就是 `aUnder`。从镜头正在看的那个表面回去的那一段，问的是那个表面，而且量的是光走的那条斜线、不是垂直深度。镜头自己泡在里面的那一段，就是那层雾。还有镜头和它正透过看的水面之间那一段，问的是那张面。这片湖以前把同一个问题答了三遍——那个 alpha、一层照抄空气平方指数律的雾（每米 0.14）、还有烘进去的吸收——三遍之间在两米厚的水上差着 **48** 的亮度。那个 alpha 还是这片湖唯一挡在镜头和天空之间的东西，所以它只在镜头在水外时才画，从水下看它一分钱不花：它把一片又浅又亮的湖底藏了起来，却把一片又深又暗的湖底提亮了。顶点波动：`sin(t*1.7 + x*0.9 + z*0.7)*0.055 + sin(t*0.6 + z*0.25)*0.03`。这一遍是**不背面剔除**、并且**画两遍**的。不剔除，是因为水面每个方块面只有一片四边形，从下往上看它就是背面，而整帧都开着的剔除器把它扔了：站在三格深的水柱底，画面最亮的像素是 **255**、**2.73%** 的像素超过 200/255——那是穿过湖水直接看太阳；现在是 **128** 和 **0%**。画两遍，是因为光活下来多少是按颜色分的，而一次混合只能把整帧乘上一个数：第一遍把画面乘上 `存活 x (1 - F)`，第二遍加上这张面扔回来的东西、和水在光出来的路上散射进光里的东西。湖是一个闭合的体积，网格只在「水挨着空气」的地方生成面，所以同一个四边形不可能同时被看到两面：不会重复混合，也不会多长几何。
- **站在岸上湖是一面镜子，坐在船里湖是一扇窗**：水面的反射率是 Fresnel，`0.02 + 0.98 * pow(1 - cn, 5)`，问的是镜头正在看的那张面、不是问镜头，所以同一片水，顺着看它就把大半视野扔回来，垂直往下看它就把几乎全部透过去。正午，两个镜头都在同一块三米浅滩上方 30 cm，只数水盖住的那些像素：顺着看的那帧平均亮度 **105.3**，垂直看的那帧 **81.1**；而顺着看的那帧同时也更蓝（**133.1** 对 **107.4**），因为它扔回来的是天空。同样两个镜头底下那块干湖底正好反过来——**171.6** 和 **178.7**，蓝 **126.3** 和 **129.8**——这就是「一个表面」和「一块地面」的全部分别。
- **玻璃**：`BLOCKS[GLASS].alpha` 从第一次提交起就写着 0.34，却从来没有人读过。玻璃一直待在**不透明**网格里，于是城堡的温室、沉塔的窗、Lanternrow 每一户人家的窗，都是一面刷成蓝灰、既看不见也走不进去的墙。现在既不透明也不是液体的方块走第六个网格，画在所有身体之后——身体写下的深度决定它是否被看见在窗子后面；透明度作为顶点颜色的第四个字节到达。相邻的同种透明方块之间的面照旧剔除，所以一堵玻璃墙是一层的厚度，而不是一砖一层。
- **站在湖外也要看得见湖**：水曾经是整个游戏里唯一一次混合绘制。顶点着色器曾经在属性指针**已经**把 alpha 字节归一化之后，又把它除以 255——水面于是只有 0.4% 不透明度：站在镜湖外面根本看不见湖，唯一带颜色的水是你把头埋进去时呛到的那团雾。别的测试读的都是世界，这一条只能读画面：先画一帧，再把水对光做的一切从画面里全部拿掉重画一帧——定律、雾、水散射回光里的那个颜色、还有水面本身——拿掉之后就是干沙状态的湖底；两帧必须不同，覆盖画面的十分之一（**49,623** 个像素），而且不同之处要朝着水自己的蓝（其中 **47,401** 个在有水时蓝比红多、没水时不多）。要证的是颜色不是亮度：在水盖住的那批像素上，湖底的**红**掉到干时的 **0.207**，**蓝**还留着 **0.805**。往画面上刷一层染色，每个通道被削掉的比例都一样；湖不是这样——这就是水和阴影的分别。旧的那个问题——湖底自己的明暗起伏透过水面还剩多少——量下来发现说明不了什么：水面放进画面的起伏和水从湖底拿走的起伏一样多，所以在三米浅滩上方，有水那一帧比它底下那块干湖底还起伏 **2.7** 倍。
- **天空**：全屏四边形，程序化渐变 + 日月盘 + 星。这个四边形每个像素自己重建视线方向——`vDir = normalize(uFwd + uRight·aCorner.x·tanX + uUp·aCorner.y·tanY)`——所以渲染器交给着色器的基底，必须和构建视图矩阵时用的是同一套手性。以前不是：`begin()` 算的是 `up = fwd × right`，而 `M4.lookYaw` 用的是 `right × fwd`，两者正好差一个负号。只有天空读 `up`，所以方块、身体、粒子全都各在其位，唯独天空沿地平线被镜像了：屏幕上半部分采样的是地平线**以下**，拿到的是地面的颜色，而太阳的光晕坐在地平线底下。07:00、镜头放平、朝着太阳的方位看，太阳已经升起 31°，一张 300 px 的画里最亮的像素在中心以下 135 px。星星的开关看的是太阳**落下去没有**（`smoothstep` 作用在 `-uSunDir.y`），不是 `uNight`：昼夜曲线关于正午对称，07:00 时 `uNight` 还说这是 37% 的夜，而太阳已经在 29° 高，于是太阳旁边那片大白天里量出了 217 根星芒。
- **雾**：指数雾，颜色随日夜；水下换色换密度——而「在水下」是看**镜头自己**在哪个格子里，不是看身体的头在不在水下；灰雾墙内换灰色浓雾。
- **夜的黑是天光，不是一种灰**：午夜时分，每个表面只被 `uDay` 照亮——它自己颜色的 0.16——再没有别的光，于是暗色的材质（针叶 `[0.14, 0.30, 0.20]`、暗叶、屋顶瓦）落在亮度 7–10，而它背后的夜空是 17–21：一棵树、一片屋顶，看起来就是天空上被挖出来的洞。四个夜里机位量下来：整帧里 **4–42%** 的像素低于亮度 12，最暗的表面 **6.8**，天空 **17.3–21.3**；同样四个机位在 13:00 低于 12 的是 **0%**。现在天自己的颜色被**加**到每个表面上（`uAmb`，来自 `env.ambient`），开关是太阳真正落下去——就是星星已经在用的那个开关，也正是太阳自己的光结束的地方（高度角 −0.1375 时 `day` 归零），所以黄昏不动。是「加」而不是「乘」，因为问题就是这个形状：它把暗的表面抬起自己的一大半，把亮的表面几乎不抬。之后：四个机位低于 12 的都是 **0%**，最暗的表面 **15.3–17.5**，天空 **18–21.3**；白天的画面一个字节都没变，因为 13:00 到 18:00 `ambient` 都是 `[0,0,0]`。
- **湖底是在水下面的**：水以前只是在镜头和一个表面之间放了一层雾，而它做的也只有这一件事——而雾是沿距离起作用的，所以在湖的这个浓度下，3 m 远的一块碎片吃到 18%，10 m 远的吃到 86%。于是一个身体正在上面游过的湖底，保住了它在岸上那种干沙的颜色。贴着水面往下正看，整帧**比红还暖**（蓝减红 **-16.7**），而且**更亮**（平均 **137**）——比同一个镜头抬头看那片被太阳照着的皮（平均 **90**）还亮：湖底比它自己那片晒着太阳的皮更亮。缺的是这一条：到达水下某个表面的光，自己已经先从上面的水里下来了，红色先被吃掉。`BLOCKS[WATER]` 现在带着 `fogK: [0.55, 0.16, 0.06]`——这东西每一米吃掉多少日光、按颜色分开——着色器把一个表面的日光乘上 `exp(-fogK x 这个表面在水下多深)`。**深度是那个表面自己的，不是镜头的。** 静态的世界在网格建好时就把它量出来了：`buildChunk` 把这个 chunk 的每一列只走一遍（有个小缓存，因为六个构建器问的是同一个问题），找出这一列水的顶面和水面之下那段的顶，落在这一段里的每个顶点都带着「我在它下面多少」上传，以 1/8 m 为一步，作为第三个字节挨着明暗和自发光标记（`aUnder`）。**而「这一列」这个问题对一类面来说是错的问题，湖底正是由这类面组成的。** 网格看得见、正挨着水的那张面，改把它的表面高度交进去，因为一张水下面的角可以坐在隔壁那块实心里，那里没有任何一列水能伸到它下面：按点去问就答「干的」，那个角就被照成沙滩的颜色。这个网格贴水生成的 5,366 张面里，有 **644** 张至少有一个角是这样被回答的——一共 **1,619** 个角，最糟的那个在 (74, 5, 95)，它上面 6 m 就是湖面——而在画面上，它们就是湖底上那些奇怪的亮点：一个贴在水面的镜头往下看，透过至少三米水看到 **70,980** 个湖底像素，其中 **137** 个回来时比蓝还暖、**35** 个亮过 140、最亮的 **176**，而这片湖底自己的平均是 60。改成按面去问，每个角都有答案，那 137 个一个不剩：**0** 个比蓝还暖、**0** 个超过 140、最亮 **83**。一个顶点仍然取自己那一列和四邻里最深的那个，这就是湖盖住的那块石头的面是湿的、而湖底下面一个洞的顶不是湿的原因。系数本身只进画面一次，就是 `liquidAbsorb()` 出来的 `env.liqK`。没烘进去的东西——一个身体（它的顶点每帧重建）、一颗掉在湖底上的果实——绘制调用被交给*那个东西*自己站在里面的那一列的表面（`liquidSurfaceAt()`，身体还有它自己的 `wSurf`，是它在自己 update 里收集的）；围着你看的那块方块的那圈描线框什么都不拿，因为它自己发光，而自己发光的东西不是靠穿过湖下来的太阳照的。世界自己的网格也什么都不拿：它们的深度是跟着网格一起来的。**「读一列」这件事归世界所有**：`liquidSurfaceAt()` 是这一列的表面、以高度表示，物理文件里的 `waterTop()` 是同一列、以*格子*表示，两者对不含水的列都答 **-1**，所以两套约定不可能在「这一列到底在不在湖里」上吵架——全谷扫过去 **2,029** 列是湿的、**2,327** 列是干的，没有一个不一致。指数对深度是线性的，而且故意不是雾的那个平方指数律：雾是沿视线方向的散射（第一米里什么都没有，一百米处全是），而下来的日光是被吸收，吸收从第一米就开始吃红——而这正是一个在四米浅滩上涉水的身体的视线所在。**之后**，正午，一个在六米浅滩水面下 60 cm 的镜头：往下看，蓝减红 **+81.3**、平均 **66.4**；抬头看那片晒着太阳的皮，**+104.3**、平均 **83.2**——皮比底亮，这是它必须在的顺序；在 9 m 底的湖底上，**+71.4**、平均 **51.4**。**一臂之外的湖底是同一个问题，而那层雾答不上来**：那里的镜头站在岸上、在水外面，它和那块湖底之间根本没有雾——够到那块湖底的是同一条定律，问的是镜头正透过看的那张面。量的是十字正前方那一块，不是整帧（整帧会把远处的湖平均进来）：两米深的湖底，蓝比红多 **+82**、平均亮度 **92**。把定律关掉，同一块变成红比蓝多 **69**、平均 **187**——一块从来没泡过水的湖底的颜色。同一块、底再往下五米，读到 **+80**、平均 **59**：底越往下它越丢红而蓝留着——这就是定律和染色的分别。**回去的那一段是沿着光线量的、不是垂直量的**：那一段以前是「湖底在自己水面下多深」——一条垂直线——而镜头泡在其中的那层雾一直是沿着光线量的；一帧拿到哪一个，由 `Math.floor(lens.y)` 决定，而这个正好在水面线上翻。一个在四米浅滩水面下 5 cm 的镜头，顺着 7 度的俯角看它的湖底，戴着整层浑浊；同一处往上 5 cm，它就被交给你只有一条垂直深度，镜头一越过水面线，浑浊就离开了画面。量的是十字正前方 2–5 m、水下 3–4 m 的那块湖底，正午：镜头在线下 5 cm 时，平均亮度和蓝减红是 **69.8 / 80.6**，在线上 **81.3 / 71.3**，线上 5 cm **87.4 / 72.6**，线上 30 cm **88.6 / 67.0**——镜头越高、湖底越干，这就是那个 bug——而湖底自己的红回到 **31.3** 和 **42.4**，可它在线下本该是 **19.3**。现在垂直那一段被放到了光线上（`vert * d / abs(vEye.y)`，上限是这条光线自己的长度：一块四米厚的水被 17 度的俯角去看是 13 m 的水，而这条光线走不到 13 m）。之后：线下 **69.8 / 80.6**，线上 **69.8 / 80.4**，上 5 cm **76.9 / 80.7**，上 30 cm **78.4 / 76.8**，同样三个镜头下湖底的红是 **19.4 / 27.5 / 30.5**。笔直往下看时，两种量法本来就是同一条线，那里一点都没动：越过水面线是 **72.4 / 72.4 / 72.6**，改前改后一样。还有那些灯：着色器对一块自己发光的碎片会打折这层雾，好让山谷对面的灯笼还是灯笼——而那个折扣是写在着色器里的常数 **0.75**，湖在里面没有发言权。灯水母停在沉塔的轮廓上，所以游进它们中间的身体会面对一圈灯：离那圈 3.6 m 时，画面回来的是亮度 **246** 的像素、99 分位 **180**、**0.72%** 超过 200/255——一个坐在湖底上的太阳。这个折扣现在是水那一行上的 `fogEmis`（**0.15**），经 `env.emisKeep` 到达着色器，空气的 0.75 仍是默认值，所以在空气里画的一帧逐字节没变。之后：那一圈灯平均 **52**、99 分位 **134**，超过 200/255 的一个也没有。
- **粒子**：单 draw call，900 个上限（发光种子、水花、变形烟雾）。一粒光不是一张表面：它是被**加**到画面上的，所以水没法往它身上刷颜色——水对它做的事，是把它发出去、正往镜头走的那束光吃掉一部分；而在这之前，粒子根本没被问过。六十个气泡在镜湖水下 0.4-2.9 m 处放出，离着一个泡在水面下 60 cm 的镜头 4-8 m，回来时盖住 **429** 个采样像素、平均亮度 **140**，其中 **197** 个亮过 140、最亮的 **222**，而它们背后、同一个镜头下的湖底只有 **66..70**——就是湖底从前那些奇怪的亮点，湖底自己早就修好了，它们还飘在那儿。之后：**303** 个像素、平均 **101**、它们的红从 **69** 掉到 **20**、最亮 **150**、超过 140 的只剩 **15** 个。一粒光坐在自己那片水面下多深，像静态世界的深度一样作为一个属性到达，而且量在画出来的那一刻、不是放出那一刻——气泡会往上走，它已经爬出来的那片水就不在了。这一段路也是**沿着光线**量的：一个吊在水下 2.5 m 的气泡，从正上方看还留着 **32** 的红，同样的距离顺着 20 度俯角看过去——那是 7 m 的湖而不是 2.5 m——只留着 **2**。镜头泡在其中的水问的是同一个问题：湖里 8 m 外的一粒光留着 **2** 的红，2 m 外的留着 **42**；水面上方一米的水花，从水下 3 m 看是 **20**，从水下 30 cm 看是 **70**。空气里的一粒光、从空气里看，一滴水都不走：exp(0) 是 1，而它被画进去的那一帧，和这条定律存在之前画的那一帧逐字节相同。
- **镜头**：无论第几人称，镜头都**正好指向鼠标指的方向**。落在后面的是身体（`faceYaw`），身体有质量。镜头曾经朝准星缓动，那就是 bug：W 往屏幕并没有指着的方向跑，高亮框也停在准星并没有指着的那格方块上。`cam.yaw` / `cam.pitch` 已经删掉——镜头剩下的状态只有距离和视野，两者都缓动。
- **第三人称距离**：`1.5 + 2.25 × 身高`，缓动，视野再加 8°——不管身体是蛙还是熊，它在画面里占的比例大致不变。
- **不被挡住**：从身体朝镜头打一条 DDA，只认固体方块（果实和芦苇不该把镜头挡瞎）。镜头退到命中方块的**近面**再减 0.2 m，最近不小于 0.55 m。
- **进到自己的身体里**：退到那么近时镜头已经在它要拍的碰撞盒里了，这时不画身体——否则你看到的是自己头骨的内侧。
- **画面跟的是镜头，呼吸留给身体**：第三人称的镜头跟在身体后面，也会跟着身体**沉下去**。站在浅滩上，湖面在 y = 15，头是干的、在 16，镜头却在 **14.19**——已经在水下了。而画面是按身体算的，于是这个镜头拿到的是一个「旱地」画面：**3.75%** 的像素超过 200/255，最亮的像素是 **255**，可从它打出去的 **56,100 条射线里没有一条**摸到天空——每一条都先撞水。现在画面按它真正在看的这层水来染色：平均亮度 **142 -> 112.4**，蓝减红 **+33.9 -> +89.9**，最亮像素 **255 -> 210**，超过 200/255 的从 **3.45% -> 2.06%**——水自己的定律为这一帧开了（`hazeOn 1`、`hazeK [0.55, 0.16, 0.06]`），水自己的那层颜色 `[0.06, 0.24, 0.32]` 是整个拿去用的，不再是往天空色里混 85%。憋气、沾湿和气泡仍然归身体管：同一帧里水面上的头还是干的，气仍然在涨（空气余量留在 **5** 以上）。平视时镜头在水面之上，一切照旧——`fogDen` 前后都是空气自己的 **0.0075**，画面里也仍然有天空：同样那 56,100 条射线里有 **4,132** 条摸到了。这层雾现在归块自己所有：块表里水那一行的 `fogC / fogT / fogEmis / fogK`，通过 `liquidFogAt()` 去读——环境代码里那份水的颜色的第二份拷贝、彼此不相连的那份，没了。一种液体要是说出自己的按颜色定律（`fogK`），它就整个替掉空气那个平方指数雾，空气自己的浓度不动；一种液体要是只说一个浓度，它就保留空气的形状、把浓度换掉。所以第二种液体——一片沼泽、一道岩浆——会把这四件事全部自己说清楚，而环境代码一行都不用改；只有一件事它得自己说、而那是烘进去的：它自己的吸收率。那个是量进世界的顶点里的，所以它得跟深度一起烘进去，而不是从画面上读。
- **身体在它站的水里，水下那一半是湿的**：被拍的身体原来是最后画的，排在水面那一遍之后，于是它盖在湖自己的混合之上，从脚到头都是干的。人站在水深只有一格的岸边水台上，镜头在开阔水面上方 5.55 米、水面以上 2.1 米处：把水的网格关掉再画一遍，身体**后面**的湖底平均变化 **148**，而水面线以下那 **642** 个身体像素只变化 **17**，其中动过的只有 **13.2%**。现在身体跟别的身体画在同一批，排在玻璃和水之前：那些像素 **100%** 都动，平均变化 **117.7**，蓝减红从 **-16.7** 变成 **+62.8**。水面线以上那一半一点没变——前后都是 **0** 个像素——因为水不写深度，它碰不到身体已经挡在前面的那些片元。水只染色，不藏人：身体的轮廓仍有 **94.9%** 与它背后的画面不同。
- **一帧一个镜头**：`update()` 只算一次（`_camFrame`），拾取射线、高亮框、交互提示和 `render()` 都读这一帧。射线在第三人称从镜头出发、第一人称从眼睛出发，但**够得着多远（5.5 m）永远从身体量起**，不从镜头量。
- **开局那一帧属于地图**：`generate()` 决定游戏开在哪，**也决定镜头开局朝哪**，它把结果连同 `yaw` 一起交出去，叫 `N.spawn`；`init()` 用这个 `yaw`，不再写死一个常数。以前的规则只检查落脚那一格和它左右两格，从来没检查镜头开局指着的方向。它选中了离主果窖那盒暗城砖半格远的地方：第一帧 91% 的像素是 0.6 m 外的一堵墙，平均亮度 57/255，画面里一点天空都没有。走开几步之后画面才好起来——"过一会儿才好"就是这件事。现在的规则是：在果窖门附近每条街的格子上，朝四个正方向各打一束射线（8×10，视野 76°，宽高比 1.6），取离门最近、且至少有一个方向**天空 ≥8%、2 m 以内的像素 ≤15%** 的格子；万一村子以后密得没有格子过关，就退而取最不差的那个（天空 ≥3%、≤30%），而不是把人塞进墙里。灯笼镇现在开在灯柱街上，离果窖门 6.0 格，朝西沿着街看。路上少立了一根灯柱：间距正好在 x = 136 立一根，而 136 就是果窖门那一列，门一开对着一根灯柱。`node-smoke.js` 检查出生格没有被埋、并且视线方向有 3 格净空——但这条检查在旧的那个点上是**通过**的，因为它的视线正好穿过敞开的窖门；只有 `play.js` 里的画面检查（看**整帧**，不是上半帧）能看出脸贴着一堵墙。

原型实测（1280×720，SwiftShader 软渲染）：100 块全建，约 20–30 万三角面，47–400 draw call，**54–60 fps**。

### 3.3 数据与存档

- 体素：`Uint8Array(w*h*d)` = 160×48×160 = 1.23 MB。
- **高度图**：计划中有（`Uint8Array(w*d)`），原型里没有。用它来收窄网格化的 y 范围实测没有变快——重建全部 100 个区块，用与不用都是每块约 1.0 ms——而且它必须在每一次方块写入都正确，否则网格会被悄悄裁掉。网格化扫描整个区块的完整高度：时间花在面上，不花在空天上。
- 存档：`localStorage['frutaria.save.v3']`，只存**方块差分**（`diffs`）+ 玩家（位置、活力、当前形态与剩余时间）+ **身份**（`id`/`name`，见 03 §6）+ 背包 + 仓库（每处野外仓库记录种下它的 `owner` 编号）+ 重生队列（`regrow`）+ 种植队列（`growQueue`）+ 死亡散落的果实（`drops`）+ 植物效果 + 猫头鹰快递 + 背包升级 + 任务 + 时间。实测：有一棵窖树、一棵幼苗、一件在途时 2.3 KB。
- 存档是**被递回**的，不是被悄悄读入的：开始界面会引用它（第几天、时辰、背包、窖树数），按「继续」才走回那条路。主果窖属于谷地而不属于存档，所以它由地图数据重建，所有仓库按 `id` 查找——一份只记录了窖树的存档，照样有一个可以走进去的镇子。

### 3.4 界面语言

界面可以在运行时无缝切换中文与英文（按 `L`，或点 HUD 右下角的按钮）。选择记在 `localStorage['frutaria.locale.v1']`；首次进入时按浏览器语言决定。

游戏里有两类文案，它们**故意**用不同的方式翻译：

| 类别 | 放在哪里 | 用什么取 | 例子 |
|---|---|---|---|
| **界面文案** | `data/i18n.js`，每种语言一张扁平的 key → 字符串表 | `N.t('hud.cap', {u, c})` | 按钮、面板、提示、日志行 |
| **设定文案** | 就在记录自己身上：`data/fruits.js` / `creatures.js` / `world.js` / `player.js` 里的 `cn` / `en` 成对字段 | `N.disp(record)` | 果实的名字与传说、生物图鉴条目、地名、称呼 |

设定文案留在它描述的东西旁边，是因为这些数据文件就是文档要比对的"真源"（`docs-sync.js` §7 会拿 `docs/cn/` 与 `docs/en/` 的正文去核对它们）。如果把翻译搬进语言表，文档就能悄悄和设定分家。

两个值得知道的后果：

- **存档里不存任何翻译。** 仓库没有自己的名字——界面按种类叫它（`store.cellar` / `store.tree`）；任务的文案住在完成它的判定旁边。所以中文里写的存档在英文下原样读回，切换语言不可能把某个字符串冻进仓库里。`game/test/lang.js` 断言存档文件在两种语言下逐字节相同。
- **加一种语言 = 加一张表。** `data/i18n.js` 里有 `LANGS` 和每语言一个对象；`node-smoke.js` 会在各表键集不一致时直接让构建失败。

### 3.5 已知技术债

| 项 | 说明 |
|---|---|
| 无遮挡剔除 | 洞穴内仍绘制外部块 |
| 无异步网格化 | 分块网格化在启动时按 22 ms 预算分帧；玩家改动会把所在块标记为脏，再按每帧 6 ms 预算重建 |
| 生物无寻路 | 只用"朝目标 + 高度修正 + 撞墙随机偏转"，会卡在地形 |
| 无 LOD / 无流式加载 | 160³ 世界全常驻内存，正式规模需 chunk streaming |
| 无 NPC 对话树 | 老梅 / 独眼只有日志文本，没有分支对话 |
| 窖树不会被摧毁 | 棕熊拆树的判定未接入（掠夺与邮递已实现） |
| 雨蛙形不脱水 | `dryTimer` 已在数据里，判定已接入，但 HUD 没有皮肤湿度条（04 §3） |
| 无身份服务 | `id` 是本地随机生成的，不是服务器签发；窖树已有 `owner`，但主果窖公用、没有共享权限模型（见 03 §6） |
| 只有两种语言 | 加第三种语言要在 `data/i18n.js` 多写一张扁平表，并且数据文件里每条带设定文案的记录（`cn` / `en` 成对字段）都要多一个字段 |
| 新的危险是看不见的 | 北岭的冷是代码在跑的规则，但没有霜、没有呼出的白气、没有 HUD 提示——唯一会告诉你的是日志一行，玩家可能到死都没弄明白自己是怎么没的；而猫头鹰在白昼被晃白，说到底只是多加了一层雾 |
| 区域文案从来不显示 | `data/world.js` 里每个区域都带一段 `desc`，但没有任何界面读它。02 的地图圣经是唯一让这些文字见到读者的地方，而且它只有中文，语言切换也管不到它 |
