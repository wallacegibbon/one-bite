# 07 · 美术 · 音频 · 技术方案

[English: ../en/07-art-audio-technical.md](../en/07-art-audio-technical.md)

## 1. 美术方向

**体素，但不是 Minecraft。** 参考：《Minecraft》的方块语言 + 《Trove》的高饱和调色 + 吉卜力的"植物是有意图的"。

三条硬规则：

1. **一切植物都有"想做的事"**：果实自发光（想被看见）、藤蔓向下（想找水）、蘑菇成环（想圈地）。
2. **建筑是长出来的，不是砌的**：灯笼镇的房子是木框架 + 苔土填墙；星坠堡是城砖 + 辉石灯；果园遗迹是一圈断墙围着谷地最老的树。
3. **光只有三种来源**：太阳/月、辉石与余烬（自发光方块）、果实（果实方块自己发光，摘下来拿在手里也发光），以及一种动物（灯水母的部件是自发光做的——但**谷地没有任何一具你能穿的身体会发光**）。**没有环境补光**——夜里没带荧光菇就是真的看不见。

### 面光照（烘焙，非实时）

每个面按法线给固定亮度，再叠顶点 AO：

| 面 | 亮度 |
|---|---|
| +Y（顶） | 1.00 |
| +Z | 0.88 |
| +X | 0.78 |
| −X | 0.66 |
| −Z | 0.58 |
| −Y（底） | 0.42 |

AO 四档：`[1.00, 0.78, 0.60, 0.46]`，按顶点三个邻块（边、边、角）计算。

这张表是给有硬边的方块用的。方块可以声明 `soft: 1`：面之间的明暗次序还在，但最低不低于 **0.74**，而且完全不吃 AO（`SOFT_S = 0.55 + 0.45·s`）。需要它的是云（16）：云也是方块，所以它以前也走这张表、也吃周围云层给的顶点 AO，一块被上面的云压着的底面测出来是自身颜色的 0.42 × 0.46 = 0.19。云本身是 94% 的白，于是结果是一团飘在亮天空里的深灰疙瘩——看起来就是天上的一块黑。画面里量：一朵云现在平均 **113**，它背后的天空是 92；把这个标记去掉，云平均 **70**，比它背后的天空还暗。灰障的墙是用同一个方块做的，所以灰障现在看着像淡雾柱子，而不是像石头。

树冠用同一个标记，理由也一样。一团树冠就是一堆叶子方块，它的底面就是你站在树下时看到的那个面，而 AO 在它下面采到的那一圈邻块**就是**这团树冠本身：树下那圈暗就是树。所以五个树冠方块（树叶 7、针叶 8、银叶 9、暗叶 27、柳叶 28）也都是 `soft: 1`。

这之后剩下的就是 AO 本身：它问的是"这块面在不在缝里"，却被当成明暗规则来读。一块朝着开阔天空的面按定义不在缝里，可树冠的底面却拿到最暗那一档，因为围着它的那圈实体正是同一团树冠。所以现在每块面还要问一遍：沿自己的法线看出去，多远才碰到东西——连续 `OPEN_R = 4` 格干净空气就完全不吃缝隙压暗；两格之内就有实体就全额保留，那正是山崖、屋檐和洞口需要的那道接触阴影；两者之间按比例插值。底面也会往 soft 的底面亮度抬上去，因为表里把底面压到 0.42 的理由是"没人会去看底面"，而这一条对一块悬在开阔空气里的面并不成立。

全图量一遍，只数那些沿法线有连续八格干净空气的面——也就是玩家会衬着天空看到的那些面，共 107,880 个：改之前 **60,506** 个渲染出来低于 60/255，占 56%，平均 73，最差 10。只加曝光这一项降到 19,277（18%）；再加上树冠的标记，**15,421 个（14%）**，平均 93，最差 39。剩下的是面表在照吩咐办事：一块暗方块的 −Z 面就是暗，那是那个假太阳，不是洞。把这条射线放宽成五条里取最宽的一条也量过，没有任何变化，所以射线保持笔直。多出来的这条射线量不出代价：100 个 chunk 整图重建前后都是 ~100 ms。画面里量同一件事：全图 216 个视角，亮度低于 55、且五像素内有亮度高于 130 的天空的像素，从占画面 **1.46%** 降到 **0.68%**。同一个指标在两个低太阳的时刻（07:00、17:00）是 **0.53%**，所以正午是最坏的情况，不是最走运的一次。`game/test/play.js` 在玩家真的会站到的两处读画面——一棵针叶树冠底下，和灯笼路上方那圈城镇屋顶：悬着的面可以比天空暗，但它的像素至少四分之一要到 **45**/255、最暗的二十分之一要过 **35**。把着色改回去，树冠这两个数是 31 和 24，屋顶是 22 和 19。

### 生物模型

体素部件拼装，每部件一个网格 + 一个 pivot。部件可以声明 `parent`，于是四肢有了关节——肩到肘，髋到膝。部件按绑定姿势书写，而猫头鹰的绑定姿势是收拢的翅膀：栖着的猫头鹰才是你一天里看得最多的那个形状。

**所有模型都朝 +Z**，而这个游戏里"朝向 `yaw`"指的是方向 `(sin yaw, -cos yaw)`：yaw 0 是北（-Z），yaw 往 +X 增大。把 +Z 转到这个朝向的旋转因此是 `PI - yaw`，而且它只存在于一处：`M4.faceY`。写成 `yaw + PI`（三个调用点以前都是这么写的）只有在正南正北时才碰巧正确，其余朝向都会把身体沿 Z 轴镜像：从背后看，往东走的身体露出的是脸；第一人称的手指向侧面；谷地里的动物只要往东或往西走就是在倒着走。`camera` 那一步的角度检查看不见这件事——镜像的模型角度一模一样——所以 `game/test/play.js` 改读画面：把身体摆在四个正方向上各站一次，镜头在它背后，把头顶投影到屏幕上，要求每一个方向看到的都是后脑勺（头发），而不是脸。

| 动画 | 用途 | 公式 |
|---|---|---|
| `flap` | 上臂（翅根） | `rz = −sign·beat·(0.22+0.78·air)`，`beat = sin(t·11)`，下拍满幅、回收只有它的 0.42。对称的正弦是风车；下拍硬、回收软才是翅膀 |
| `fold` | 前臂（parent 是翅） | 只在上拍折叠：`rz = sign·(beat<0 ? −beat·0.5 : 0)·air` |
| `walk` | 大腿 / 上臂 | `rx = sign·sin(t·7+phase)·move·0.75` —— 所有身体共用一个步频；原来按物种覆盖的 `gait` 只为梁蛛存在过，跟着它一起删了 |
| `knee` | 小腿 | 膝盖只朝一个方向弯：`rx = sign·(0.25+0.85·max(0,sin(t·7+phase)))·(0.35+0.65·move)` |
| `elbow` | 前臂 | 随摆动带一点跟随 |
| `twist` | 躯干 | `ry = sin(t·7+phase+π)·move·0.16` —— 肩与腿反向摆 |
| `nod` | 头 | `rx = sin(t·1.9)·(move·0.06+0.02)` |
| `wag` | 尾 | `ry = sin(t·1.6)·(move·0.5+0.12)` |
| `bob` | 身体 | 在天上时它**就是**拍翅的节奏：`dy = −max(0,beat)·0.16`，翅膀往下压，身体就往下沉。两条互不相干的正弦，会让飞行的身体看起来像一具身体上螺栓固定着两个会动的零件。在地上 `dy = sin(t·2.2)·(move·0.12+0.05)` |
| `pulse` | 雨蛙的喉、水母的伞 | 是缩放，不是旋转 |

部件还可以声明 `air:[rx,ry,rz]` 和 `crouch:[rx,ry,rz]`：身体离地时它取什么姿势、腿在蓄力时它取什么姿势。权重来自物理，不是来自"现在画的是哪种动物"的猜测——`air` 是身体实际离地多高，`crouch` 是它的脚从上次起跳后在地上停了多久，`squash` 是它落地时的速度，作为缩放作用在整个身体上。不跳的身体永远不会被画成在跳。

部件还可以声明 `swimKick: 1`（身体在游的时候，这一部件是蹬腿的驱动件）和 `swimPose: [rx,ry,rz]`（游的时候它被保持在这个姿势）。`swim` 是调用方传过来的第四个信号，而且只对**数据给了它游速的身体**打开：**人在湖里是趟水**，因为人的模型没有游泳部件，游戏里也没有人的泳姿。雨蛙不在水面上跑。两条后腿**一起**蹬，每秒 4.2 次，而不是步频的每秒 7 步；膝盖在划水的前半程收进来、脚在后半程向后伸直——向后那半程才是推水的半程；前腿折起来贴在身侧。蹬腿时故意丢掉 `sign` 的镜像——同步的一对腿在时间上不是镜像的，而几何的镜像模型数据里已经写了。量的是渲染器要上传的那些角度：陆地上两条后腿大腿彼此相差 1.24 / 1.50 / 1.31 弧度（交替），水里是 0.000（一起），前腿则从交替变成保持 0.55 弧度。量的是画面：从正后方看的轮廓，与它自己的镜像吻合度，蹬腿时 **0.976**，跑的时候 **0.944**。画面这一条是这对检查里松的那一半——从正后方看，一条腿在前、一条在后只让轮廓变 6%——所以这个说法同时也在角度本身上读一遍，那才是它真正被说出来的地方。

**身体本身还剩一个姿势信号：`bank`（侧倾）。** 被空气或水托着的身体转弯时向内侧倾；用脚走的身体不侧倾，因为这个速度下没有东西会侧倾。它不是部件动画——渲染器把整个身体绕它自己的朝向轴转一个角——而且玩家和每一只生物用的是同一条规则、同一组数：每秒转过的弧度乘 0.11，夹在 0.45 以内，再以 4.5 缓动。量出来：一只猫头鹰被按着转过四分之一圈，峰值 **0.251 rad**（14°）；一头棕熊被同样转过四分之一圈，始终是 **0**；把这段旋转从绘制里拿掉，同一个身体的两帧完全一样——**0** 个像素不同，而留着它是 **1395** 个。睡在枝上的鸟不算：栖木上的猫头鹰是原地转身，那不是侧倾。

**脚踩在一个面上，就是站在这个面上。** 以前接触标记只由"碰撞不得不拦下来的那次移动"点亮；身体总是停在它上次撞到的那个面外 0.0005 m 处，而下面那一格要等脚探进去 0.001 m 才会被采到——所以一帧得先沉下 0.0015 m，脚下那个面才会重新被看见。陆地上重力够用（一帧 0.006 m），所以标记只是一帧一帧地闪，缓动的姿势把它盖住了。在水里它不够用：浮力抵掉大部分重量，阻力留下约 0.05 m/s 的终端下沉速度，一帧 0.0008 m，于是水底每三帧才被采到一次。于是在水深只有一格的地方趟水的身体——镜湖的湖岸有 183 个这样的列——它整个时间都站在湖底上，却被报成悬空：`air` 姿势缓到 0.42 就停在那里，转向只剩三分之一的推力（accel 12，本该是 34）。所以位移算完之后，脚在实体 2 cm 以内、身体又不在往上走，就是站着；2 cm 正是自动上台阶用来把身体放回它刚爬上的那道坎面的距离，也远小于身体真的离面之后攒下的落差（第一帧 0.006 m，第五帧 0.10 m）。量出来：站在这样一个列里，身体 **100%** 的帧都在底上、姿势是 **0**——改之前是 50% 和 0.42——沿着这条湖岸趟水，两秒走出 **5.19 m**，脚一直是落着的；而且这个标记不是胶水：身体走出一个单级台阶，接下来 40 帧里有 **18** 帧离地，姿势缓到 **0.88**，落下 **1.0 m**。

模型自己**不带缩放**。给身体定尺寸的只有一个数：`data/creatures.js` 里的碰撞盒（`size`，单位米）。模型用单位方块建模，生物的 `scale` 把单位换成米——所以模型和碰撞盒是同一具身体的两份写法，两者一旦不一致，玩家就会被自己看得见、却碰不到的几何体穿过去。`game/test/node-smoke.js` 会把每个模型按它所属生物的碰撞盒量一遍，超出就失败：模型的水平半径最多比盒子的半宽多出 0.1 m，最高点最多比盒子的高多出 0.06 m。量的是**半径**而不是宽度，因为碰撞盒是一个不随身体转动的正方形底面——正面刚好放得下的模型，转个身照样捅进墙里。这道闸门立起来之前，棕熊离中心有 1.26 m，而它的盒子只有 0.70 m 宽：等于有 0.56 m 的熊在它靠着的那面墙里，雨蛙的鼻尖也超出自己的盒子 0.13 m。

灯水母是唯一**没有盒子可量**的模型：游戏里没有任何东西会撞上它（你从灯中间游过去），而它不结果实，所以也没有玩家会穿上它。于是改用它图鉴上写着的尺寸来核对——按 `scale` 0.16 算，**宽 0.61 m，从伞顶到最长那条腕的尖端 0.74 m**。

5 个模型：human, owl, frog, bear, jelly。
第一人称手部 4 种：hand, talon, web, claw。

## 2. 音频方向（未实现，正式设计）

**没有配乐，只有"环境 + 材质"。**

| 层 | 内容 |
|---|---|
| 底噪 | 风（云顶最强）、水（镜湖）、滴水（洞穴）、叶响（深鹿林"没有风也会响"） |
| 生物 | 雨后蛙鸣（12 声部循环，玩家变雨蛙时加入第 13 声部）、猫头鹰单音、水下的低频和声（只有浸水时听得见） |
| 交互 | 采摘 = 一声"啵"；失活 = 干裂声；变形 = 骨节重组 + 一次吸气 |
| UI | 图鉴翻页 = 纸；果窖开 = 木门 |
| 危险 | 灰雾墙内所有声音被"吸掉"（低通截止随深度降到 400 Hz） |

**变形时的音频规则**：变形瞬间，当前形态对应生物的叫声以玩家位置为中心播放，并持续整个形态期（音量随移动变化）。这让玩家"听见自己是什么"。

## 3. 技术方案（原型）

### 3.1 零依赖自研 WebGL1 渲染器

为什么不用 three.js：原型必须能**双击 `game/index.html` 直接跑**（`file://` 协议下 ES module 会被 CORS 拦），且体素渲染的需求很窄。

全部代码为经典 `<script src>` 全局脚本，挂在 `window.FRUTARIA` 命名空间下。

| 文件 | 职责 |
|---|---|
| `src/engine.js` | mat4、MeshBuilder、着色器、Renderer（视锥剔除、天空、粒子） |
| `src/world.js` | 方块表、体素存储、分块网格化（含 AO）、DDA 射线拾取 |
| `src/worldgen.js` | 值噪声/fbm 地形 + 结构生成（城堡/镇/洞/湖/浮岛/森林） |
| `src/models.js` | 5 个模型 + 4 种第一人称手部 + 部件动画矩阵（带父子链，所以四肢有关节） |
| `src/entities.js` | Player（AABB 碰撞/呼吸/飞行）、Creature（态度驱动 AI）、Particles |
| `src/game.js` | 主逻辑：果实/背包/腐坏/仓库/任务/存档/渲染循环 |
| `src/ui.js` | HUD、旋转小地图、背包条、仓库面板、图鉴、帮助、死亡 |
| `src/i18n.js` | 语言状态与查找：界面文案用 `t(key)`，设定文案用 `disp(record)` |
| `src/main.js` | 输入绑定、主循环、启动流程 |
| `data/*.js` | **设定真源**：fruits / creatures / world / player / i18n |

### 3.2 渲染

- **分块**：16×48×16，10×10 = 100 块。每块 6 个网格：`[不透明, 自发光, 水, 道具, 道具自发光, 玻璃]`。
- **面剔除**：固体不透明邻居的面不生成。
- **视锥剔除**：从 MVP 提取 6 个平面（列主序取行：`row3 ± row0/1/2`），按块中心球体测试。
- **自发光层**：单独网格，`emisBoost` 提升，不受日夜光照影响。
- **水**：单独网格，混合用的透明度取自方块表：`BLOCKS[WATER].alpha` 由 `def()` 一次性折进顶点颜色的第四个字节，绘制调用里不再抄第二份同一个数。这个数现在是 **0.72**：0.62 的时候，湖底的明暗对比透过水面还剩下 38%，湖看起来像地上一个坑，而不是像水。顶点波动：`sin(t*1.7 + x*0.9 + z*0.7)*0.055 + sin(t*0.6 + z*0.25)*0.03`。这一遍是**不背面剔除**画的：水面每个方块面只有一片四边形，从下往上看它就是背面，而整帧都开着的剔除器把它扔了。站在三格深的水柱底，画面最亮的像素是 **255**，**2.73%** 的像素超过 200/255——你是穿过湖水直接看太阳。现在是 **128** 和 **0%**。湖是一个闭合的体积，网格只在「水挨着空气」的地方生成面，所以同一个四边形不可能同时被看到两面：不会重复混合，也不会多长几何。
- **玻璃**：`BLOCKS[GLASS].alpha` 从第一次提交起就写着 0.34，却从来没有人读过。玻璃一直待在**不透明**网格里，于是城堡的温室、沉塔的窗、Lanternrow 每一户人家的窗，都是一面刷成蓝灰、既看不见也走不进去的墙。现在既不透明也不是液体的方块走第六个网格，画在所有身体之后——身体写下的深度决定它是否被看见在窗子后面；透明度作为顶点颜色的第四个字节到达。相邻的同种透明方块之间的面照旧剔除，所以一堵玻璃墙是一层的厚度，而不是一砖一层。
- **站在湖外也要看得见湖**：水曾经是整个游戏里唯一一次混合绘制。顶点着色器曾经在属性指针**已经**把 alpha 字节归一化之后，又把它除以 255——水面于是只有 0.4% 不透明度：站在镜湖外面根本看不见湖，唯一带颜色的水是你把头埋进去时呛到的那团雾。别的测试读的都是世界，这一条只能读画面：先画一帧，再把所有水网格关掉重画一帧，要求两帧必须不同，而且不同之处要朝着水自己的蓝。同一对画面还回答第二个问题：**湖底透过水面还剩多少**。透过水面看到的明暗起伏，比关掉水面时同一批像素的起伏，必须小于 **0.34**（0.72 量出来是 0.29，旧的 0.62 是 0.38）。
- **天空**：全屏四边形，程序化渐变 + 日月盘 + 星。这个四边形每个像素自己重建视线方向——`vDir = normalize(uFwd + uRight·aCorner.x·tanX + uUp·aCorner.y·tanY)`——所以渲染器交给着色器的基底，必须和构建视图矩阵时用的是同一套手性。以前不是：`begin()` 算的是 `up = fwd × right`，而 `M4.lookYaw` 用的是 `right × fwd`，两者正好差一个负号。只有天空读 `up`，所以方块、身体、粒子全都各在其位，唯独天空沿地平线被镜像了：屏幕上半部分采样的是地平线**以下**，拿到的是地面的颜色，而太阳的光晕坐在地平线底下。07:00、镜头放平、朝着太阳的方位看，太阳已经升起 31°，一张 300 px 的画里最亮的像素在中心以下 135 px。星星的开关看的是太阳**落下去没有**（`smoothstep` 作用在 `-uSunDir.y`），不是 `uNight`：昼夜曲线关于正午对称，07:00 时 `uNight` 还说这是 37% 的夜，而太阳已经在 29° 高，于是太阳旁边那片大白天里量出了 217 根星芒。
- **雾**：指数雾，颜色随日夜；水下换色换密度——而「在水下」是看**镜头自己**在哪个格子里，不是看身体的头在不在水下；灰雾墙内换灰色浓雾。
- **粒子**：单 draw call，900 个上限（发光种子、水花、变形烟雾）。
- **镜头**：无论第几人称，镜头都**正好指向鼠标指的方向**。落在后面的是身体（`faceYaw`），身体有质量。镜头曾经朝准星缓动，那就是 bug：W 往屏幕并没有指着的方向跑，高亮框也停在准星并没有指着的那格方块上。`cam.yaw` / `cam.pitch` 已经删掉——镜头剩下的状态只有距离和视野，两者都缓动。
- **第三人称距离**：`1.5 + 2.25 × 身高`，缓动，视野再加 8°——不管身体是蛙还是熊，它在画面里占的比例大致不变。
- **不被挡住**：从身体朝镜头打一条 DDA，只认固体方块（果实和芦苇不该把镜头挡瞎）。镜头退到命中方块的**近面**再减 0.2 m，最近不小于 0.55 m。
- **进到自己的身体里**：退到那么近时镜头已经在它要拍的碰撞盒里了，这时不画身体——否则你看到的是自己头骨的内侧。
- **画面跟的是镜头，呼吸留给身体**：第三人称的镜头跟在身体后面，也会跟着身体**沉下去**。站在浅滩上，湖面在 y = 15，头是干的、在 16，镜头却在 **14.19**——已经在水下了。而画面是按身体算的，于是这个镜头拿到的是一个「旱地」画面：**3.75%** 的像素超过 200/255，最亮的像素是 **255**，可从它打出去的 **56,100 条射线里没有一条**摸到天空——每一条都先撞水。现在画面按它真正在看的这层水来染色：超过 200/255 的 **0%**，最亮 **150**，平均亮度 **142.9 → 109.5**，`fogDen 0.14`，颜色朝 `[0.06, 0.24, 0.32]` 混了 85%。憋气、沾湿和气泡仍然归身体管：同一帧里水面上的头还是干的，气仍然在涨（空气余量留在 **5** 以上）。平视时镜头在水面之上，一切照旧——`fogDen` 前后都是 **0.0075**。
- **身体在它站的水里，水下那一半是湿的**：被拍的身体原来是最后画的，排在水面那一遍之后，于是它盖在湖自己的混合之上，从脚到头都是干的。人站在水深只有一格的岸边水台上，镜头在开阔水面上方 5.55 米、水面以上 2.1 米处：把水的网格关掉再画一遍，身体**后面**的湖底平均变化 **148**，而水面线以下那 **642** 个身体像素只变化 **17**，其中动过的只有 **13.2%**。现在身体跟别的身体画在同一批，排在玻璃和水之前：那些像素 **100%** 都动，平均变化 **117.7**，蓝减红从 **-16.7** 变成 **+62.8**。水面线以上那一半一点没变——前后都是 **0** 个像素——因为水不写深度，它碰不到身体已经挡在前面的那些片元。水只染色，不藏人：身体的轮廓仍有 **94.9%** 与它背后的画面不同。
- **一帧一个镜头**：`update()` 只算一次（`_camFrame`），拾取射线、高亮框、交互提示和 `render()` 都读这一帧。射线在第三人称从镜头出发、第一人称从眼睛出发，但**够得着多远（5.5 m）永远从身体量起**，不从镜头量。
- **开局那一帧属于地图**：`generate()` 决定游戏开在哪，**也决定镜头开局朝哪**，它把结果连同 `yaw` 一起交出去，叫 `N.spawn`；`init()` 用这个 `yaw`，不再写死一个常数。以前的规则只检查落脚那一格和它左右两格，从来没检查镜头开局指着的方向。它选中了离主果窖那盒暗城砖半格远的地方：第一帧 91% 的像素是 0.6 m 外的一堵墙，平均亮度 57/255，画面里一点天空都没有。走开几步之后画面才好起来——"过一会儿才好"就是这件事。现在的规则是：在果窖门附近每条街的格子上，朝四个正方向各打一束射线（8×10，视野 76°，宽高比 1.6），取离门最近、且至少有一个方向**天空 ≥8%、2 m 以内的像素 ≤15%** 的格子；万一村子以后密得没有格子过关，就退而取最不差的那个（天空 ≥3%、≤30%），而不是把人塞进墙里。灯笼镇现在开在灯柱街上，离果窖门 6.0 格，朝西沿着街看。路上少立了一根灯柱：间距正好在 x = 136 立一根，而 136 就是果窖门那一列，门一开对着一根灯柱。`node-smoke.js` 检查出生格没有被埋、并且视线方向有 3 格净空——但这条检查在旧的那个点上是**通过**的，因为它的视线正好穿过敞开的窖门；只有 `play.js` 里的画面检查（看**整帧**，不是上半帧）能看出脸贴着一堵墙。

原型实测（1280×720，SwiftShader 软渲染）：100 块全建，约 20–30 万三角面，47–400 draw call，**54–60 fps**。

### 3.3 数据与存档

- 体素：`Uint8Array(w*h*d)` = 160×48×160 = 1.23 MB。
- **高度图**：计划中有（`Uint8Array(w*d)`），原型里没有。用它来收窄网格化的 y 范围实测没有变快——重建全部 100 个区块，用与不用都是每块约 1.0 ms——而且它必须在每一次方块写入都正确，否则网格会被悄悄裁掉。网格化扫描整个区块的完整高度：时间花在面上，不花在空天上。
- 存档：`localStorage['frutaria.save.v3']`，只存**方块差分**（`diffs`）+ 玩家（位置、活力、当前形态与剩余时间）+ **身份**（`id`/`name`，见 03 §6）+ 背包 + 仓库（每处野外仓库记录种下它的 `owner` 编号）+ 重生队列（`regrow`）+ 种植队列（`growQueue`）+ 死亡散落的果实（`drops`）+ 植物效果 + 猫头鹰快递 + 背包升级 + 任务 + 时间。实测：有一棵窖树、一棵幼苗、一件在途时 2.3 KB。
- 存档是**被递回**的，不是被悄悄读入的：开始界面会引用它（第几天、时辰、背包、窖树数），按「继续」才走回那条路。主果窖属于谷地而不属于存档，所以它由地图数据重建，所有仓库按 `id` 查找——一份只记录了窖树的存档，照样有一个可以走进去的镇子。

### 3.4 界面语言

界面可以在运行时无缝切换中文与英文（按 `L`，或点 HUD 右下角的按钮）。选择记在 `localStorage['frutaria.locale.v1']`；首次进入时按浏览器语言决定。

游戏里有两类文案，它们**故意**用不同的方式翻译：

| 类别 | 放在哪里 | 用什么取 | 例子 |
|---|---|---|---|
| **界面文案** | `data/i18n.js`，每种语言一张扁平的 key → 字符串表 | `N.t('hud.cap', {u, c})` | 按钮、面板、提示、日志行 |
| **设定文案** | 就在记录自己身上：`data/fruits.js` / `creatures.js` / `world.js` / `player.js` 里的 `cn` / `en` 成对字段 | `N.disp(record)` | 果实的名字与传说、生物图鉴条目、地名、称呼 |

设定文案留在它描述的东西旁边，是因为这些数据文件就是文档要比对的"真源"（`docs-sync.js` §7 会拿 `docs/cn/` 与 `docs/en/` 的正文去核对它们）。如果把翻译搬进语言表，文档就能悄悄和设定分家。

两个值得知道的后果：

- **存档里不存任何翻译。** 仓库没有自己的名字——界面按种类叫它（`store.cellar` / `store.tree`）；任务的文案住在完成它的判定旁边。所以中文里写的存档在英文下原样读回，切换语言不可能把某个字符串冻进仓库里。`game/test/lang.js` 断言存档文件在两种语言下逐字节相同。
- **加一种语言 = 加一张表。** `data/i18n.js` 里有 `LANGS` 和每语言一个对象；`node-smoke.js` 会在各表键集不一致时直接让构建失败。

### 3.5 已知技术债

| 项 | 说明 |
|---|---|
| 无遮挡剔除 | 洞穴内仍绘制外部块 |
| 无异步网格化 | 分块网格化在启动时按 22 ms 预算分帧；玩家改动会把所在块标记为脏，再按每帧 6 ms 预算重建 |
| 生物无寻路 | 只用"朝目标 + 高度修正 + 撞墙随机偏转"，会卡在地形 |
| 无 LOD / 无流式加载 | 160³ 世界全常驻内存，正式规模需 chunk streaming |
| 无 NPC 对话树 | 老梅 / 独眼只有日志文本，没有分支对话 |
| 窖树不会被摧毁 | 棕熊拆树的判定未接入（掠夺与邮递已实现） |
| 雨蛙形不脱水 | `dryTimer` 已在数据里，判定已接入，但 HUD 没有皮肤湿度条（04 §3） |
| 无身份服务 | `id` 是本地随机生成的，不是服务器签发；窖树已有 `owner`，但主果窖公用、没有共享权限模型（见 03 §6） |
| 只有两种语言 | 加第三种语言要在 `data/i18n.js` 多写一张扁平表，并且数据文件里每条带设定文案的记录（`cn` / `en` 成对字段）都要多一个字段 |
| 新的危险是看不见的 | 北岭的冷是代码在跑的规则，但没有霜、没有呼出的白气、没有 HUD 提示——唯一会告诉你的是日志一行，玩家可能到死都没弄明白自己是怎么没的；而猫头鹰在白昼被晃白，说到底只是多加了一层雾 |
| 区域文案从来不显示 | `data/world.js` 里每个区域都带一段 `desc`，但没有任何界面读它。02 的地图圣经是唯一让这些文字见到读者的地方，而且它只有中文，语言切换也管不到它 |
